# Sources and validation — TLS trust paths

Reviewed October 26, 2026. Original synthesis; source publication dates are not discovery dates. This skill specializes the existing RBVM closure workflow, rather than replacing its population, rollout, and authorization requirements.

## Primary evidence

- [Cloudflare, eMudhra response](https://blog.cloudflare.com/emudhra-certificate-compromise/), published October 20, 2026, retained research lead reviewed October 26. Practical motivation: services can delegate trust differently, bundled/custom stores need separate attention, updates require activation, and another client's test does not prove application protection. We do not copy incident-specific package/version recommendations into a timeless skill or claim our fixture reproduces that compromise.
- [Python 3.12 ssl documentation](https://docs.python.org/3.12/library/ssl.html), rolling documentation, publication date unspecified; page identified itself as 3.12.16 at review. `PROTOCOL_TLS_CLIENT`, hostname verification, context lifecycle, `load_verify_locations`, `wrap_bio`, and `MemoryBIO`. Our installed Python is 3.12.14; the fixture always supplies a nonempty hostname, including on releases with weaker missing-hostname validation. Do not infer that a certificate-chain check validates peer identity.
- [OpenSSL 3.5 load-verify-locations contract](https://docs.openssl.org/3.5/man3/SSL_CTX_load_verify_locations/), versioned documentation, publication date unspecified. CAfile is processed on load; CApath is looked up as needed. This supports a lifecycle distinction, not a claim that every TLS implementation snapshots every store. The experiment separately demonstrates additive loading in the tested runtime.
- [curl TLS certificate verification](https://curl.se/docs/sslcerts.html), rolling documentation, publication date unspecified. Native/file stores and backend/build differences; HTTPS proxy and origin have distinct verification settings. No curl integration, native platform store, proxy, or network endpoint was tested.
- [Requests advanced usage](https://requests.readthedocs.io/en/latest/user/advanced/#ssl-cert-verification), rolling documentation, page identified 2.34.2. Explicit `verify`, environment bundle overrides, and the manual prepared-request environment-merge distinction. No Requests/urllib3 adapter experiment was run. Do not generalize these precedence rules to other clients.

## Experiment and failure/remedy

`python3 skills/security/tls-trust-path-verification/reproduce.py` uses only installed Python and OpenSSL. The script creates disposable fixture-only CA/leaf keys in a private temporary directory, uses `.invalid` identities, performs no network I/O, and cleans its files. No persistent credentials or host trust configuration are changed. Do not install dependencies automatically if they are absent.

Fourteen unittest methods: ten exercise or guard actual in-memory TLS handshakes; four test a deliberately small local evidence-disposition policy. Both normal and optimized execution passed with Python 3.12.14, linked OpenSSL 3.5.8; certificate generation used installed CLI OpenSSL 3.5.7. Independent review tightened rejection oracles: fixture trust failures require OpenSSL code 20 (unable to get local issuer); the hostname control requires code 62. Other certificate failures cannot stand in for the intended policy outcome. Boolean evidence checks are exact, so missing/string controls cannot silently become success.

Baseline: context loaded with fixture anchor A accepts A. Replacing its backing bundle with B does not change that context's acceptance; a separate fresh diagnostic context rejects A while the application context still accepts it. Loading B into the original context retains A. Remedy: reconstruct the context from B and observe A's certificate rejection, B's success, and wrong-hostname rejection. An already established connection can still exchange data after the file change.

The managed runtime preloaded one additional public CA into fresh contexts. An initial absolute anchor-count assertion therefore failed; it was corrected to check the one-anchor delta and actual A/B handshake outcomes. We neither removed that anchor nor claimed an empty/exclusive starting trust store. The passing untrusted-B and removed-A controls bound the fixture result despite ambient trust.

These tests do not prove deployment activation, production fleet coverage, all TLS backends, CRL/OCSP, intermediate distrust, alternative/cross-signed chains, session resumption, connection-pool replacement, proxies, pinning, mTLS, actual advisory protection, or network/SDK integration. Fresh handshakes explicitly check `session_reused` is false; existing-session resumption behavior is not exercised. A fixture result is not remediation authority.
